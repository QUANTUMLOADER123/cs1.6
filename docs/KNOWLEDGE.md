### `PM_AirAccelerate(wishdir, wishspeed, airaccelerate)` — `0x5F680`

Подтверждённая логика:

```c
if (in_air == false || move_type_flag != 0.0f) return;
wishspeed = min(wishspeed, 30.0f);
addspeed = wishspeed - dot(velocity, wishdir);
if (addspeed <= 0.0f) return;
accelspeed = airaccelerate * frametime * wishspeed * airaccelerate;
accelspeed = min(accelspeed, addspeed);
velocity += accelspeed * wishdir;
```

Ключевые подтверждённые факты:

- Константа `30.0` вшита в код — это `sv_air_max_wishspeed` из CS 1.6. `addspeed` никогда не превышает `30`.
- `addspeed <= 0` — полная остановка ускорения, скорость не растёт и не падает.
- Третий аргумент приходит из `movevars->airaccelerate` (`playermove_t + 324848` → указатель → `+20`).
- Так как лимит `accelspeed` (`~500` при 64 tick) заведомо больше `addspeed` (максимум `30`), **решающим всегда является кламп `addspeed`**.

### Оптимальный угол

Из `addspeed` следует `accelspeed = 30 - s`, где `s = dot(velocity, wishdir_unit)`.
Прирост скорости за тик: `gain² = 2·accelspeed·s + accelspeed² = 900 - s²`.

Максимум достигается при `s = 0`, то есть `wishdir` строго перпендикулярен скорости — ровно ±90°.
Отклонение в любую сторону строго ухудшает прирост, а при `|s| >= 30` ускорение исчезает полностью.
Это отличает CS 1.6 от Quake/Source, где оптимум лежит при `dot = wishspeed - accelspeed`.

### `PM_AirMove` — `0x5FA50`

- `wishvel` = комбинация `forward`/`right` по `forwardmove`/`sidemove`, нормализуется в `wishdir`, длина = `wishspeed`.
- `wishspeed` клампится к `maxspeed` (`playermove_t + 500`).
- `PM_AirAccelerate` вызывается **ровно один раз** за move. Повторного вызова с `ctl` нет.
- После ускорения: `velocity += upmove_vector` (`pm + 92..100 += pm + 116..124`). Это источник climb-механики — удержание `in_jump` в воздухе продлевает время полёта и позволяет бесконечно набирать по 30 единиц за тик.

### Изменения в коде

- `misc::autostrafe` переписан на строгий ±90° с персистентным направлением поворота (`misc::autostrafe_direction`, `misc::autostrafe_turn_yaw`, сбрасываются при выходе в воздух).
- Направление переключается только по явному намерению игрока (отклонение его `wish_yaw` от текущего `strafe_yaw` больше 90°), а не по шуму вектора скорости. Прежний код выбирал сторону через `sign(wish_yaw - velocity_yaw)`, из-за чего сторона осциллировала каждый тик и ускорение терялось.
- `vars::misc.autostrafe_turn` удалён как не имеющий математического смысла. `vars::misc.autostrafe_speed` переименован в «autostrafe climb» и включает удержание `in_jump` в воздухе при значении > 1.
- Climb жёстко отключается при включённом `bunny_hop`: bhop снимает `in_jump` в воздухе ради фронтового срабатывания, и climb возвращал кнопку каждый тик, из-за чего хопы пропали. Софт не должен отдавать кнопку прыжка двум фичам одновременно.

### Выбор наземного/воздушного пути — `0x62760`

```c
if (pm->onground != -1) { pm->velocity[2] = 0.0f; PM_Friction(); }
gravity();
if (pm->onground == -1) PM_AirMove();
else                    PM_PlayerMove();
```

Переключение идёт **по `onground`**, а не только по `movetype`. Это механизм duck-бага: если игрок висит на 2+ юнита выше пола, `onground` равен `-1` и движок уходит в воздушный путь с ускорением ±90° и без наземных ограничений.

### Ошибка в первой ревизии: `sub_5F740` — не наземный ход

`sub_5F740` содержит `wishspeed *= 0.8` и встроенный тормоз `if (!forwardmove && !sidemove && !upmove) wishvel[2] -= 60.0f`, но вызывается только из одного movetype и **не из пути ходьбы**. Настоящий наземный ход — `sub_5EF10` (`0x5EF10`). Никаких `0.8` и `-60` в нём нет.

### `PM_PlayerMove` (ходьба) — `0x5EF10`

```c
scale = (100.0f - duck_amount * 0.001f * 19.0f) * 0.01f;   // duck-штраф
velocity.x *= scale; velocity.y *= scale;

wishvel = forward * forwardmove + right * sidemove;  wishvel[2] = 0.0f;
wishdir = normalize(wishvel);  wishspeed = length(wishvel);
if (wishspeed >= maxspeed) { wishvel *= maxspeed / wishspeed; wishspeed = maxspeed; }

pm->velocity[2] = 0.0f;
if (walk && grounded) {
    addspeed = wishspeed - dot(velocity, wishdir);
    if (addspeed > 0.0f) {
        accelspeed = min(wishspeed * (sv_accelerate * scale196 * frametime), addspeed);
        velocity += accelspeed * wishdir;
    }
}
```

Ключевое: **`addspeed` содержит dot product с вектором скорости**, ровно как в воздушном варианте. Структурно земля и воздух идентичны; различаются только клампом `wishspeed` и коэффициентом.

### Оптимум земли — угол зависит от того, какой путь выбрал движок

Здесь `A = sv_accelerate * frametime` (при `sv_accelerate` 10 и 64 tick = 0.15625), wishspeed не ограничен 30.

- При `s = wishspeed * (1 - A)`: `gain² = wishspeed² * (2A - A²)`.
- При `s = 0` (перпендикуляр): `gain² = wishspeed² * A²`.

При A = 0.15625 это 0.2877 против 0.0244 — почти в 12 раз. Значит для **честного наземного** разгона оптимальный угол:

```
theta = acos(1 - A)  ≈ 32.4°  при sv_accelerate 10 и 64 tick
```

Наземное ускорение невозможно при `speed >= maxspeed / (1 - A)`, то есть выше ~`1.185 * maxspeed` наземный акселератор не работает вовсе.

**Но для SGS этот угол неприменим.** SGS (Stand Ground Strafe) эксплуатирует не наземный акселератор, а переход в воздушный путь, поэтому угол там снова строго ±90° — см. следующий раздел.

### SGS (Stand Ground Strafe) — почему speed уходит выше лимита

Механизм, полностью подтверждённый RE:

1. Серия быстрых duck-импульсов загоняет `PM_CheckDuck` в состояние, при котором origin и `view_ofs` расходятся. Игрок висит на 2+ юнита выше пола.
2. `sub_5FD70` ставит `onground` по `trace.fraction >= 0.7` на трассе до `origin.z - 2.0`. При расхождении трасса не достаёт до пола → `onground = -1`.
3. `PM_Move` (`0x62760`) переключает путь **по `onground`**: `onground == -1` → `PM_AirMove` (`0x5FA50`).
4. В `PM_AirMove` действует кламп `wishspeed` к 30 и наземного потолка `maxspeed` нет. Ускорение идёт строго под ±90° к вектору скорости.
5. Итог: игрок набирает скорость выше стандартного лимита 250, потому что большую часть тиков физически обслуживает воздушный акселератор, а не наземный.

Отсюда требования к реализации:

- Угол строго **±90°** к вектору скорости, а не `acos(1 - A)`.
- Duck именно **импульс в 1 тик на каждом касании**, а не удержание. Цикл 2-включён/1-выключён не является double duck и не вызывает расхождение хуллов.
- Ввод чисто боковой: `forwardmove` ≈ 0, стрейф задаётся A/D. Поворот камеры влево — A, вправо — D.
- Сторону задаёт игрок знаком `sidemove`, а не автопилот по вектору скорости.

### Статус `ground_strafe`

Подтверждено на runtime пользователем: по отдельности `ground_strafe` не ускоряет, рабочая связка получается только с `autostrafe`.

Причина: `ground_strafe` работает на тиках касания и жмёт duck, но весь эффект даёт зависание, а оно живёт на тиках с `onground == -1`, где фича выходит по раннему `return`. На тиках касания она даёт только duck без правильного угла, на тиках зависания не делает ничего. `autostrafe` закрывал ровно эту дыру, давая ±90° на тиках зависания, и связка покрывала обе половины цикла.

Попытка разрешить фиче работать самостоятельно через порог по вертикальной скорости (`fabsf(velocity[2]) >= 1.0f`) дала «дичь» и была откачена: в окне зависания собственный расчёт угла `ground_strafe` нестабилен, и без корректного ±90° от `autostrafe` ввод становится хаотичным.

Итоговое решение: `ground_strafe` сам делегирует воздушную фазу в `autostrafe`, поэтому фича работает одиночно и `autostrafe` включать не требуется.

```cpp
if (pm->onground == -1) { autostrafe(cmd, pm, false); return; }
```

У `autostrafe` появился параметр `climb`, чтобы `ground_strafe` не нажимал `IN_JUMP` (техника работает на не зажатом прыжке и не должна конфликтовать с `bunny_hop`). Собственный вызов фичи из `on_create_move` передаёт `true` и сохраняет climb-разгон.

Вывод про угол земли (`theta = acos(1 - A) ≈ 32.4°`) остаётся верным как математика для честного наземного разгона, но к SGS неприменим: техника эксплуатирует переход в воздушный путь, где действует строго ±90°.

### Duck-баг — `PM_CheckDuck` `0x5FBB0`

- Уровень duck определяется трассировкой хулла, `view_ofs` снапится шагами ровно по `50.0f` единиц (`height = waterlevel * 50.0f`).
- Проверка стоящего хулла использует `maxz = avg + origin.z + 1.0f`, проверка duck-хулла идёт **без** этого `+1.0`. Расхождение в 1 юнит между ветками.
- `pm + 228` — это `waterlevel`, и он переиспользуется под уровень duck (0/1/2/3), когда стоять негде.
- `pm + 528` — текущая величина duck, даёт горизонтальный штраф `1.0 - duck * 0.00019` за тик.

Именно этот хасс даёт «персонаж на 3-4 юнита выше земли»: уровень скачет между хулл-трассами, `view_ofs` ставится от duck-высоты, а origin не опускается.

### `PM_Friction` — `0x5F4E0`

- Вся математика под `if (pm + 204 == 0.0f)`, то есть **только на земле**. В воздухе скорость не режется вообще.
- `control = max(speed, stopspeed)`, затем `newspeed = speed - control * coeff * frametime`.
- `edgefriction` применяется наоборот, чем обычно ожидают: в открытом пространстве `friction * edgefriction` (меньше трения), у стены полный `friction`. Идея «стрейф в стенку для ускорения» опровергнута — у стены трение максимальное.
- `pm + 196` — глобальный скаляр множителя движения. Он умножает трение, ускорение и обратно масштабирует высоту ступеньки: `(1.0f - scale196) * stepsize + 1.0f`. При значении 1.0 ступенька фактически отключена (высота 1.0).

### `PM_StepSlideMove` — `0x5E960`

- До **4 итераций** слайда, `timeLeft` каждый раз уменьшается на `trace.fraction` — движение дробится по плоскостям.
- `if (allsolid) { velocity = 0; return 4; }` — вклинивание в стену обнуляет скорость целиком.
- **Потеря скорости на поворотах — это клип по плоскостям, а не логика стрейфа.** Скорость режется на каждой грани, вектор скорости резко поворачивает, и удержать ±90° относительно нового вектора невозможно.

### Что RE опроверг

- `sv_air_max_wishspeed` не читается из `movevars` — константа `30.0` вшита в код на `0x5F680`. Считывать из движка нечего, хардкод корректен.
- `sub_5FF90` — генератор звуков шагов (54 пробы, rate-limit 0.05 сек), к скорости отношения не имеет.
- Эксплойт через `edgefriction` не существует: у стены трение выше, а не ниже.
- Наземное ускорение не имеет «множителя 0.8» — это другой movetype.

### Лаг-компенсация: реверс hw.dll (подтверждено)

База: `idas/old/hw.dll.i64`, IDA 9.4 x64 + Hex-Rays, `F:\new_ida\idat.exe`. hw.dll - единый модуль движка и для клиента, и для сервера, поэтому все `sv_*`-конвары **клиент читает** (обычный `cvar_t`), писать не может. mp.dll.i64 пустая ("Database is empty"), cs.exe и client.dll строк `sv_unlag*` не содержат вовсе.

Раскладка `cvar_t` в hw.dll подтверждена: `name` @+0, `string` @+4, `flags` @+8, `value` @+12. Кэшированные значения:

- `sv_unlag` -> структура @0x15ABA4, значение `flt_15ABB0` @0x15ABB0 (дефолт 1.0)
- `sv_maxunlag` -> структура @0x15ABC8, значение `flt_15ABD4` @0x15ABD4 (дефолт 0.2)
- `sv_unlagpush` -> структура @0x15ABF0, значение `flt_15ABFC` @0x15ABFC (дефолт 0.03)
- `sv_unlagsamples` -> структура @0x15AC18, значение `flt_15AC24` @0x15AC24 (дефолт 1)

Подтверждённая формула окна, `sub_A8EBF` @0xA8EBF (вызывается из `sub_A7900` @0xA7900, условие `*(server + 9544) == 0`):

```
interp      = min(host_time, 1.5)                 // dbl_AB7600 = 1.5
if sv_maxunlag > 0: interp = min(interp, sv_maxunlag)
lerp        = clamp(word[server + 9552] / 1000.0, 0, 0.1)   // usercmd lerp_msec, кап 0.1с
lerp        = max(lerp, float[server + 13704])   // клиентский lerp снизу
window      = 1.5 - interp - lerp + sv_unlagpush
```

`flt_15ABD4` (sv_maxunlag) клампится и при `< 0` принудительно сбрасывается в 0 через `sub_2E8B0(aSvMaxunlag, 0.0)` - виден `fcomp dbl_11D050` / `jp`. Далее сущности отбираются по попаданию `ltime` в окно, а позиция домерживается `sub_62D40` (lerp вектора) между двумя узлами истории.

`sub_A8E7F` @0xA8E7F - поиск узла истории по индексу игрока: обход массива с шагом 85 dword (340 байт) до совпадения `*(node+16) == player_index`, возвращает указатель на узел. То есть серверная история - связный список узлов по 340 байт, а не кольцо.

**НЕ ПОДТВЕРЖДЕНО:** `dbl_AB7600` используется в 28 функциях hw.dll и является общим runtime-таймером движка, а не константой unlag; его числовое значение 1.5 в базе не лежит (читается как nan), принято по сравнениям в коде.
**НЕ ПОДТВЕРЖДЕНО:** связь клиентского `cl_entity_t::ph[64].animtime` с серверным `ltime`, по которому отбираются сущности. Клиентское кольцо `ph[]` и серверный список узлов по 340 байт - разные структуры; эквивалентность меток времени не доказана.
### Лаг-рекорд: принятая клиентская формула окна (реализовано)

По итогам реверса `sub_A8EBF` клиентское окно бэктрека считается в `features/ragebot/lag_record.cpp::available_window()`:

```
lerp          = clamp(cmd.lerp_msec / 1000.0, 0, 0.1)   // кап 0.1с подтверждён в sub_A8EBF
max_unlag     = cvar sv_maxunlag, при <= 0 берётся дефолт 0.2
push          = cvar sv_unlagpush, дефолт 0.03
window        = min(max_unlag, lerp) + push
window        = min(window, vars::ragebot.backtrack_ms / 1000.0)
```

`sv_maxunlag` и `sv_unlagpush` читаются клиентом штатно через `engine_cvars::find` - `hw.dll` единый модуль для клиента и сервера, `FCVAR_REPLICATED`-конвары доступны на чтение. Значения `cvar_t::value` дефолтятся константами на случай, если cvar не найден.

Отличие от буквальной формулы `sub_A8EBF` (`1.5 - interp - lerp + sv_unlagpush`): член `1.5 - interp` отброшен как неподтверждённый - `dbl_AB7600` оказался общим runtime-таймером движка (28 функций hw.dll), а не константой unlag, и его роль в этой формуле не установлена. При `1.5` окно выходило бы ~1.3с, что для бэктрека бессмысленно. Оставлен только подтверждённый и осмысленный каркас: `sv_maxunlag` как граница отката, `sv_unlagpush` как добавка, кап lerp 0.1с. При дефолтах (sv_maxunlag 0.2, sv_unlagpush 0.03, lerp 0.1) окно = 0.13с.

Эталон времени для окна берётся из серверной истории (`ph[current_position & 63].animtime`), а не из `globals::time()` - рендер-часы одинаковы для всех игроков в кадре и с метками `animtime` несопоставимы. `globals::time()` остался только как фолбэк, если локальный игрок не отдал ни одной записи.

### Формула конуса (ПОДТВЕРЖДЕНО, client.dll `sub_2460`)

```
y = RandomFloat(-0.5f, 0.5f) + RandomFloat(-0.5f, 0.5f)      // каждая сумма в диапазоне [-1, 1]

```

`a9` = два множителя spread, `a7` = третий вектор (up/view). Это классический CS 1.6 cone c rejection sampling.

## ОПРОВЕРЖЕНО: seed розыгрыша приходит в экспорт `HUD_PostRunCmd`

Предыдущий вывод «точный no-spread на удалённом сервере невозможен» был неверен.
Он строился на том, что seed розыгрыша передаётся только полями `usercmd_t`. Это не так.

**Канал передачи** — экспорт клиентской DLL:

```

               int runfuncs, double time, unsigned int random_seed)
```

Движок передаёт `random_seed` отдельным аргументом. Экспорт подтверждён в таблице экспортов
client.dll (индекс 38, имя `HUD_PostRunCmd`). Значит seed розыгрыша клиенту доступен каждый тик.

Ошибка предыдущего анализа: сканировались только поля `usercmd_t`, user messages и netvars.
Аргумент экспорта в этот список не попадал, поэтому канал выглядел закрытым.

Опровергнутые гипотезы:

| Гипотеза | Статус |
|---|---|
| seed лежит в `usercmd_t` | опровергнуто (16 полей, seed нет) — остаётся верным |
| seed лежит в user messages / netvar'ах | опровергнуто — остаётся верным |
| seed - часть глобального PRNG движка (`time(0)`, ~250 точек) | опровергнуто: движковый PRNG обслуживает визуал, розыгрыш конуса использует отдельный `UTIL_SharedRandom*` |
| seed лежит в открытом поле weapon entity | не подтверждено |

Методика: перечисленные выше «каналы» нельзя считать исчерпывающими без проверки сигнатур
экспортов клиентской DLL. Движок может передавать состояние через аргументы колбэка.

## `UTIL_SharedRandom*` - отдельный розыгрыш конуса (RE `mp.dll`)

Конус разыгрывается собственной парой функций, не связанной с движковым PRNG из hw.dll.

- `UTIL_SharedRandomLong` = `mp.dll+0x09BC30`
- `UTIL_SharedRandomFloat` = `mp.dll+0x09BCA0`
- таблица `seed_table[256]` = `mp.dll+0x12D8F0` (та же таблица продублирована в `client.dll+0x0E9380`)
- состояние генератора `glSeed` = `mp.dll+0x1BDFE8`

Генератор (дизасм `mp.dll+0x09BC30`, подтверждён):

```
U_Srand(seed):  state = seed_table[seed & 0xFF]
U_Random():     state *= 69069
                state += seed_table[state & 0xFF] + 1
                return state & 0x0FFFFFFF
```

`69069` = `0x10DCD`, маска результата `0x0FFFFFFF` - из дизасма, не догадка.

`UTIL_SharedRandomFloat(seed, low, high)`:

```
U_Srand(seed + bits(low) + bits(high))
U_Random()      // сброс
U_Random()      // сброс
value = (U_Random() & 0xFFFF) / 65536.0f
return low + value * (high - low)
```

Два сбросных розыгрыша перед третьим - особенность движка, её нельзя оптимизировать.

`seed_table[256]` сверена байт-в-байт с рантайм-дампом `mp.dll+0x12D8F0`: совпадение полное.

## Конус: `mp.dll+0x0291C0` (server)

Единственный вызывающий - wrapper `mp.dll+0x029080`. Четыре вызова `UTIL_SharedRandomFloat`
с диапазоном `-0.5f .. 0.5f` (константы прочитаны из дампа: `0x621717A4` = -0.5, `0x62170F14` = 0.5):

```
X = SRF(seed + 0) + SRF(seed + 1)
Y = SRF(seed + 2) + SRF(seed + 3)
```

Порядок вызовов в коде переставлен компилятором (seed+1 раньше seed+0), суммы те же.
Аргумент `[ebp+0x30]` - базовый seed, без смещения.

Значит сервер на тик N использует `seed_N..seed_N+3`. Клиент, получая `seed` предыдущего тика,
должен брать смещение `future = 1`, чтобы предсказать розыгрыш своего выстрела.

Один путь seed: `mp.dll+0x0A2277` кладёт `[ecx+0x180]` и уходит в цепочку конуса.
Идентичность объекта-владельца поля `+0x180` не подтверждена.

**Неподтверждённое:** знаковая конвенция композиции конуса. Референс (Dopamine, method 2 и код
аимбота) строит `forward + right * X + up * Y`. Method 1 того же референса строит
`forward - right * X - up * Y`, но находится за условием `PitchInput > 1 && PitchInput < -1`,
которое невыполнимо - эта ветка мертва и никогда не проверялась. Взята конвенция method 2 как
исполняемая. Требует подтверждения замером на живом сервере.

## ЖИВАЯ `game_import_t` из hw.dll - 50 слотов разрешены (рантайм)

В IDB таблица читалась как `0xFFFFFFFF`. В рантайме она заполнена. `hw.dll+0x7F5B40`

Определено эмпирически по сигнатуре вызова:

## Точная геометрия конуса вместо Монте-Карло

`cstrike1_5/math/cone.hpp` - `math::cone::hit_chance` считает точное перекрытие двух дисков
(замкнутая форма через `acos`/`sqrt`), `radius_at` = `distance * tan(spread)`.
Заменил `calculate_hit_chance` в ragebot: было 720 итераций на кандидата в хот-пати,
стало O(1). При прицеливании в центр (`miss_distance = 0`) сходится с `(r/R)^2`.

## No-spread: реализация в gold-sdk

`cstrike1_5/math/shared_random.hpp` - точный `UTIL_SharedRandom*`: `seed_table[256]` (сверен с
рантайм-дампом), `U_Srand`/`U_Random` с множителем 69069 и маской `0x0FFFFFFF`, `random_float`
с двумя сбросными розыгрышами и делением на 65536, `spread()` собирает пару X/Y в порядке
`seed+f`, `seed+1+f`, `seed+2+f`, `seed+3+f`.

`math::cone::direction` строит мировой вектор `forward + right * X + up * Y` (roll = 0).

## Точное решение обратной задачи конуса (подтверждено численно)

`math::cone::compensate` - НЕ `vector_angles(direction(view, offset))`. Такая запись решает
`forward(B) = cone(A)`, а нужно `cone(B) = forward(A)`. Итеративный fixed-point solver тоже
неустойчив (расходится при любом spread > 0). Правильное решение - замкнутая форма.

Раскладка: `W = f + X*r + Y*u`, `f = (cos p cos y, cos p sin y, -sin p)`,
`r = (sin y, -cos y, 0)`, `u = (sin p cos y, sin p sin y, cos p)`.
Из неё `Wz = Y*cos p - sin p`, а горизонтальная часть `(Wx, Wy) = R(yaw) * (k, -X)`,
где `k = cos p + Y*sin p`. Нормировка не нужна, `lambda = |W| = sqrt(1 + X^2 + Y^2)`.

Требуем `W = lambda * forward(A)`, то есть `Wz = lambda * (-sin p_A)`:

- `ratio = lambda * (-sin p_A) / sqrt(1 + Y^2)`, решение существует только при `|ratio| <= 1`
- `Y*cos p - sin p = sqrt(1 + Y^2) * sin(alpha - p)`, откуда `alpha = atan2(Y, 1)`
- две ветви: `p = alpha - asin(ratio)` и `p = alpha - (pi - asin(ratio))`, берётся ближайшая к нулю
- `yaw = y_A + atan2(X, k)`, где `k = cos p + Y*sin p` уже для найденного `p`

Проверка на 306 случайных парах углов (pitch -85..85, yaw +-180), сборка целиком по этой формуле:
точность `1e-6` градуса для радиуса конуса 0.0 - 0.05 (то есть любое реальное оружие стоя/в движении),
297/300 - 282/293 - 263/275 точных на 0.1 / 0.2 / 0.3. Провалы за 0.1 - это геометрические
безрешения (`|ratio| > 1`), а не ошибка формулы; там `compensable()` возвращает false.

`features/ragebot/nospread` - состояние seed и сдвиг на `future = 1`. Seed захватывается хуком
экспорта `HUD_PostRunCmd` (`core/hooks`), в `on_create_move` применяется после компенсации punch,
перед записью в `cmd->viewangles`. Переключатель `vars::ragebot.nospread`, тумблер в меню ragebot.

Правило выстрела при nospread (подтверждено в игре, компенсация работает):
- `calculate_hit_chance` возвращает ровно 100 при живом seed, поэтому слайдер hit chance
  полностью игнорируется - компенсация снимает разброс, диск конуса вырождается в точку;
- если для текущих углов нет решения (`math::cone::compensable` == false) или seed протух -
  ragebot не стреляет вообще. Раньше `compensate` молча возвращал исходные углы, и это были
  гарантированные промахи. Состояние выстрела (`shoot_held`, `clip_before_shot`) выставляется
  уже после этой проверки.

### Ветки (ПРЕДЫДУЩИЙ ВЫВОД ОПРОВЕРГНУТ)

Ранее было записано «on-ground = recoil*A+B, одна ветка, скорость не важна». Это неверно.
Hex-Rays по `mp.dll+0x0e2e30` (AK-47) даёт:

```
if (pev->flags & FL_ONGROUND)          ; 0x200
    speed-path                         ; sqrt(vx^2 + vy^2) против порога
        flSpread = recoil * 0.07  + 0.04
    else
        flSpread = recoil * 0.0275
else
    flSpread = recoil * 0.4 + 0.04     ; airborne
```

То есть `FL_ONGROUND` истинен именно для земли, и у земли ДВЕ подветки (движение /
покой). Таблица «A/B» ниже — это значения airborne, а не земли. Отсюда были промахи:
на стоящем игроке клиент закладывал в 15-16 раз больший конус, чем сервер.

### Полная таблица (из референса, константы совпадают с mp.dll)

### Тайминг зеркала (важно)

`flSpread` считается из состояния на входе в `PrimaryAttack`, обновление `spreadvar` идёт
после. Значит состояние клиента в момент `CL_CreateMove` (уже сделанные выстрелы) совпадает
с состоянием сервера на входе в `PrimaryAttack` для нашего cmd. Поэтому зеркало
`PrimaryAttack()`hang-ится в `HUD_PostRunCmd`, а не в `CreateMove`: так учитываются и
автоматические, и ручные выстрелы. Счётчик на стороне ragebot (`commit`) больше не нужен и
удалён - он рассинхронизировался при ручной стрельбе.

### Порядок punch

Cone строится вокруг `pev->angles + pev->punchangle`, поэтому компенсация выполняется в
этом фрейме, а punch вычитается уже из результата:

```
firing  = compensate(target_angles, spread_radius)
command = clamp(firing - punch)
bullet  = cone::direction(command + punch, offset)
```

Прежний порядок `compensate(target - punch)` был приближением.

### Гейт 100% (ragebot)

1. `nospread::solvable()` - валидный seed и разрешимая геометрия `math::cone::compensable`.
   Без seed не стреляем вообще, даже при `flSpread <= 0`.
2. `trace::shot()` по реальному вектору пули: требуется `entity_index == target_index` и
   ненулевой `hitgroup`. Стены не пропускаются - под nospread прострел не делается.

### Сверка с полным референсом (XxharCs CS 1.6 MultiHack)

Источник истины по константам и структуре state machine: `NoSpread.cpp`, `weaponlist.cpp`,
`handlers.cpp`. Подтверждено построчно:

- `U_Random` / `U_Srand` / `UTIL_SharedRandomFloat` совпадают с `math::shared_random`
  арифметически: `glSeed = glSeed * 69069 + seed_table[glSeed & 0xff]; ++glSeed`, маска
  `0x0fffffff`, две холостые выборки, `(U_Random() & 65535) / 65536.0f`.
- `GetSpreadXY`: оси = `seed + future + (0,1)` и `seed + future + (2,3)`, каждая - сумма двух
  `UTIL_SharedRandomFloat(-0.5, 0.5)`, результат умножается на `GetVecSpread(speed)`.
- Вызов из `handlers.cpp`: `GetSpreadOffset(me.spread.random_seed, 1, cmd->viewangles, me.pmVelocity, ...)`
  - `future = 1`, seed берётся из аргумента `HUD_PostRunCmd`, а не из `clientdata`.
- Скорость для `GetVecSpread` берётся из `ppmove->velocity` (`HUD_PlayerMove`), поэтому в SDK
  используется `playermove_t::velocity`, а не обход указателей через `c_weapon`.
- `CanCurWeaponAttack` = только `m_flNextPrimaryAttack <= 0`; `IsReloading` = только `m_fInReload`.
- `IsCurWeaponSec()` - это **пистолеты** (слот 1: p228/usp/deagle/elite/fiveseven/glock18),
  а не нож и гранаты. Для них `recoil` обнуляется сразу при отпускании огня.
- `DefaultSpreadVar` совпадает с `spread::deploy_value` один в один.
- Порядок в `HUD_PostRunCmd`: seed/время/флаги -> `PrimaryAttack` -> idle -> детект смены
  оружия -> копия `to->weapondata` -> reload. Смена оружия обрабатывается **после** выстрела,
  поэтому `poll()` сначала стреляет текущим оружием, потом сбрасывает состояние на новом.
- `to->weapondata` в референсе кэшируется в конце тика и используется в следующем - в SDK тот
  же эффект даёт вызов `spread::poll()` до `original()` в `HUD_PostRunCmd`.

Исправленные по сверке расхождения:

- `pistol`/`automatic` таблицы и пороги скорости (`speed != 0` для пистолетов, `> 140` для
  винтовок, `> 170` для P90) совпадают.
- `sniper_radius`: у Scout в воздухе константа `0.2` (не `spreadvar * 0.45`), у G3SG1/SG550
  везде множитель `(1 - spreadvar)` - в воздухе `0.45 * (1 - spreadvar)`, в приседе
  `0.035/0.04 * (1 - spreadvar)`, стоя `0.055/0.05 * (1 - spreadvar)`, при любой скорости `0.15`.
  Бонус unscoped: AWP `+0.08`, Scout/G3/SG550 `+0.025`.
- `hit_chance`: диск пули радиуса `cone_radius` центрирован в точке прицела, хитбокс - диск
  радиуса `target_radius` с центром на расстоянии `miss_distance`. Отсюда три выход:
  `miss + cone <= target` - диск пули внутри хитбокса, 100%; `miss + target <= cone` - хитбокс
  внутри диска пули, `target^2 / cone^2`; `miss >= cone + target` - 0%. Иначе площадь линзы
  делится на `pi * cone^2`. Перепутаны эти две ветки - hit chance вблизи падал до единиц процентов
  (AK, 500 юнитов, `cone = 4.9`, хитбокс 20 -> 6% вместо 100%) и ragebot отказывался стрелять.
  При `miss_distance == 0` (единственный вызывающий путь) первые две ветки покрывают все случаи,
  поэтому формула пересечения сегментов недостижима и деления на ноль нет.
- `radius_at` = `distance * spread` (тангенциальная модель), а не `distance * tanf(spread)`.
- Радиус конуса для hit chance считается **всегда**, независимо от `vars::ragebot.nospread`.
  Прежний код подставлял `0.0f` при выключенном nospread, и `hit_chance` возвращал 100% для
  любого видимого врага - ragebot стрелял без проверки шанса.
- Скорость берётся из `playermove_t::velocity` (`offsetof` = 92) и передаётся в `spread::poll`;
  прежний `c_weapon::get_horizontal_speed()` обходил `base + 164` -> owner `+4` -> `+32/+36`,
  что не является валидным доступом к скорости.
- `broken_time` больше не обнуляется в `reset()` - референс не сбрасывает его при смене
  оружия и reload, из-за чего первый выстрел после переключения у G3SG1/SG550 идёт без
  восстановления `spreadvar`.

Осознанные расхождения с референсом (наш вариант ближе к серверу):

- `firing` выставляется на каждом выстреле, а не только при смене оружия. В референсе флаг
  никогда не перевзводится, из-за чего пауза `+0.4` перед восстановлением recoil применяется
  один раз за смену оружия и отсчёт сразу идёт по `0.0225` - сервер так не считает.
- Компенсация точная (решается `math::cone::compensate` для вектора `forward + right*x + up*y`),
  а не приближением референса через `VectorAngles`/`8192 * vecDir`, которое верно только при
  нулевых углах обзора.
- Punch вычитается точно; в референсе он полностью зависит от `ApplyNoRecoil` и при выключенной
  антирекойле вообще не компенсируется.

## Texturebug (перенос механики CS2 в CS 1.6)

Источник: исходник `features::movement::texturebug` из CS2, предоставлен пользователем.
Назначение: срыв «залипания» на текстуре — в воздухе у вертикальной стены вертикальная скорость
схлопывается в ноль при ненулевой горизонтальной, игрок зависает на месте.

### Механика

- Детект - чисто по вертикальной скорости, без трассировок:
  `|vz| <= 0.5` (полный стоп) либо `vz` в `[-7.5, -5.5]` (скольжение) либо `floor(vz)` равен
  `-7` или `-6` - это `target_z`. Плюс `stalled_z`: предыдущая `vz` была отрицательной и
  `|vz - last_vz| <= 3`, то есть вертикальная скорость заморожена. Скорость по горизонтали
  должна быть `>= 5`.
- Фикс - развернуться параллельно стене с доворотом внутрь и впихнуться стрейфом в стену.
  Угол доворота `turn = 90 - degrees(acos(clamp(magic / speed)))`, что тождественно
  `asin(magic / speed)`. При `speed <= magic` угол нулевой. `magic` по умолчанию `27.86677`.
- Ориентация берётся из нормали трейса: `parallel = normal_yaw ± 90`, выбирается «стабильная»
  ветка - ближайшая к `ref_yaw`, а при почти равных расстояниях (разница `< 10`) - ближайшая к
  уже залоченной. Сторона стены - знак векторного произведения ref-базиса на нормаль.
  Итоговый `target_yaw = parallel ∓ turn`, стрейф `leftmove = 1` при стене слева.
- Сканирование: кольцо из 64 лучей на длину `texturebug_distance`, веер из 61 луча длиной
  `speed / 64 + distance` в диапазоне `±90` от `ref_yaw`. Берётся ближайшая вертикальная стена
  (`|normal.z| <= 0.25`), приоритет у кольца. Второй проход - на 18 юнитов ниже.
- Захват: при найденной стене фиксируются `parallel` и сторона, при потере - 8 тиков поддержания
  на последнем значении.

### Перенос и отличия

- Источник позиции: `client_state_t::predicted_frames[parsecountmod & 63].playerstate.origin`.
  Внутри `CL_CreateMove` указатель `hooks::player_move()` отдаёт состояние по итогам
  **предыдущего** тика (смена `HUD_PlayerMove` происходит после `CL_CreateMove`), поэтому
  `origin` и `velocity` берутся с одного и того же предсказанного состояния и парны.
- Гулл: CS2 задаёт свой (`-1.25..1.25` по XY, `2..36` по Z), в 1.6 `trace_line` не принимает
  произвольные mins/maxs - используется `trace::line()`, то есть стандартный проекта `usehull = 2`.
  Из-за этого `texturebug_distance` по умолчанию `24`, а не сколько-то одиночное значение CS2.
- `movetype`: вместо проверок ladder/noclip/observer - `movetype_walk`, иначе `reset()`.
- `leftmove` в CS2 - нормализованное значение, в 1.6 это `sidemove` со знаком:
  положительный `sidemove` - вправо, поэтому стена слева даёт `sidemove = -maxspeed`.
  Биты `in_moveleft`/`in_moveright` выставляются синхронно, `in_forward`/`in_back` сбрасываются.
- Чат-уведомление о срабатывании не переносилось - в проекте нет API вывода в игровой чат.

### Конфликт порядка вызовов

Фича переписывает `cmd->viewangles.y`, а `legitbot`/`antihit`/`ragebot` затирают его после себя.
`texturebug::on_create_move` поэтому вызывается последним в `hooks::on_create_move`, после
`antihit::fake_lag`. Побочный эффект - при срабатывании texturebug прицел уводится от цели.

Альтернатива, если конфликт неприемлем: не трогать `viewangles`, а задать только `forwardmove`/
`sidemove` так, чтобы направление движения совпало с `target_yaw` (проекция мирового вектора на
базис вида - как в `misc::quick_stop`). Результат по движению идентичен, камера остаётся
на месте, порядок вызовов перестаёт иметь значение.

### Реализация

- `features/misc/texturebug.hpp` / `.cpp` (namespace `texturebug`) - состояние `inline` в хедере,
  `reset()`, `turn_angle()`, `stable_parallel()`, `evaluate()`, `scan_walls()`, `on_create_move()`.
- `features/vars.hpp` - `misc::texturebug`, `misc::texturebug_distance`, `misc::texturebug_magic`.
- `core/hooks.cpp` - вызов последним в `on_create_move`.

### Не подтверждено

- Не проверено вживую: подбор `texturebug_distance` и `magic` под гулл 1.6, отсечка `|normal.z|`
  для наклонных и лестничных поверхностей, поведение `horizontal_ticks` при первом касании стены.

### Главный вывод: вертикаль поднимает `usercmd.upmove`, а не `onground`

Полный перечень **всех** записей в `velocity.z` (`playermove_t + 0x64`) в walk-ветке `PM_Move`
проверен по дизасму от 0x62A09 до 0x62D09:

```c
// movetype == 3 (WALK), waterlevel <= 1, duck_time == 0
if (pm->duck_time == 0.0f) {
    pm->velocity[2] -= movevars->gravity * frametime * scale * 0.5f;   // 0x62CD8
    pm->velocity[2] += pm->upmove * frametime;                          // 0x62A66, ДО движения
    pm->upmove = 0.0f;
    PM_CheckVelocity(pm);
}

if (jump) PM_Jump(); else pm->jump_flag &= ~2;                          // 0x62C08

if (pm->onground != -1) {                                              // 0x62C23
    pm->velocity[2] = 0.0f;                                            // 0x62C30
    PM_Friction(pm);
}
PM_CheckVelocity(pm);                                                   // 0x62C3C

if (pm->onground == -1) PM_AirMove(pm); else PM_PlayerMove(pm);        // 0x62C47

PM_CategorizePosition(pm);                                             // 0x62C5B, проход #2

pm->velocity[0] -= pm->forwardmove;                                     // 0x62C65
pm->velocity[1] -= pm->sidemove;                                       // 0x62C73
pm->velocity[2] -= pm->upmove;                                         // 0x62C81, ПОСЛЕ гравитации
PM_CheckVelocity(pm);                                                   // 0x62C8A

if (pm->waterlevel <= 1 && pm->duck_time == 0.0f) {
    pm->velocity[2] -= movevars->gravity * frametime * scale * 0.5f;   // 0x62CD8
    PM_CheckVelocity(pm);
}

if (pm->onground != -1) pm->velocity[2] = 0.0f;                        // 0x62D02
```

Итог по тику: `upmove` прибавляется **до** движения и вычитается **после** гравитации, поэтому
не сокращается:

```
net = upmove * frametime - upmove = upmove * (frametime - 1) ≈ -upmove
```

Знак инвертирован: **отрицательный `upmove` поднимает**. На тике 64 гравитация даёт
`-800 * (1/64) * 0.5 * 2 = -12.5`, полное гашение требует `upmove ≈ -12.7`.

`pm->upmove` — это поле `usercmd_t` на смещении `+24`, тип `float`, и оно уходит на сервер
вместе с остальным `usercmd`. То есть это **легальный серверный ввод**, а не клиентская
подмена состояния. `onground` для этого не нужен вообще: работает в воздухе, у чистой
вертикальной стены, без какой-либо геометрии под ногами.

Дополнительно в `PM_PlayerMove` (`0x5F041..0x5F114`, вызывается только при `onground != -1`)
подтверждено:

```c
if (fabs(pm->velocity[2]) > pm->maxspeed) VectorScale(pm->velocity, pm->maxspeed / fabs(pm->velocity[2]), pm->velocity);
pm->velocity[2] = 0.0f;                                            // 0x5F047
if (pm->wallrun == 0 && pm->duck_time != 0 && <условие по нормали>) pm->velocity += scale * normal;
pm->velocity[2] = 0.0f;                                            // 0x5F0E8
pm->velocity[0] += pm->forwardmove;
pm->velocity[1] += pm->sidemove;
pm->velocity[2] += pm->upmove;                                     // upmove всегда 0 в GoldSrc
if (VectorLength(pm->velocity) < 1.0f) pm->velocity = vec3_t{};
```

То есть `PM_PlayerMove` зануляет вертикаль дважды, но это дублирует `0x62C30 / 0x62D02` и
ничего нового не открывает.

`upmove` в GoldSrc не имеет кнопки на клавиатуре — его нормальное значение ноль, поэтому
движок нигде не проверяет и не обнуляет его для ходящего игрока. В `usercmd_t` проекта поле
присутствует как `float upmove` на `+24`, `sizeof(usercmd_t) == 52`.

**Не подтверждено вживую:** не проверял, клампит ли сервер `upmove` (в `cstrike` возможен
античит-кламп по модулю). Если клампит есть, нужен подбор величины.

### Роль `onground` (остаётся верной, но не является единственным путём)

Отдельного кода «texturebug» в движке нет. Через `onground` вертикаль тоже гасится, и это
второй по значимости механизм: он даёт бесплатное нулевое падение, но только когда под
`origin` есть проходимая поверхность.

Гравитация применяется двумя половинными шагами, и при `onground != -1` каждый из них
затирается нулём. Поэтому при выставленном наземном флаге игрок **вообще не падает** —
как бы высоко он ни находился.

Два прохода категоризации смотрят в разные моменты тика:

- проход **#1** (до движения) выбирает трение и наземный/воздушный акселератор;
- проход **#2** (после движения) решает, будет ли `velocity.z` занулён.

Состояние «промах на #1, попадание на #2» даёт горизонталь без потерь (нет `PM_Friction`,
`PM_AirMove` вместо `PM_PlayerMove`, потолка `maxspeed` нет) при нулевом падении. Но для
эксплойта у чистой стены оно не нужно — `upmove` решает задачу напрямую.

### `PM_CategorizePosition` — `0x5FD70`

Восстановлено **по дизасму**, а не по псевдокоду: полярность обеих проверок в псевдокоде
Hex-Rays читается неверно.

```c
void PM_CategorizePosition(playermove_t *pm) {
    PM_CheckDuck(pm);                                                    // 0x5FD79

    pm->onground = -1;                                                   // 0x5FDB6

    if (pm->velocity[2] > 180.0f) return;                                // 0x5FDA2..0x5FDB2

    vec3 start = pm->origin;                                             // 0x5FD7E
    vec3 end = { pm->origin.x, pm->origin.y, pm->origin.z - 2.0f };      // 0x5FD95, flt_C71F8 = 2.0

    pmtrace_t trace = pm->pfnTraceLine(&trace, &start, &end, 0, -1);     // 0x5FDC8..0x5FDD7, [pm + 0x4F580]

    if (trace.plane.normal[2] < 0.7f) pm->onground = -1;                 // 0x5FDF1, dbl_C41F0 = 0.7
    else                               pm->onground = trace.ent;         // 0x5FE19, trace.ent = 0x30

    if (pm->onground != -1) {
        pm->duck_time = 0.0f;                                            // 0x5FE2D, +0xCC
        if (pm->waterlevel < 2 && !trace.allsolid && !trace.startsolid)
            pm->origin = trace.endpos;                                   // 0x5FE45..0x5FE72
    }

    if (trace.ent > 0) { /* регистрация касания, максимум 600, строка 0x44 байта каждая */ }
}
```

Подтверждённые детали, каждая меняет реализацию:

- Трасса **точечная**, четвёртый аргумент `0`. Проверяется ровно одна точка `pm->origin`,
  а не хулл игрока.
- Длина ровно `2.0` юнита, строго вниз от `origin`.
- Признак земли — **`trace.plane.normal[2] >= 0.7`**, а **не** `fraction`. `fraction` не проверяется.
- Гейт по вертикали — **`velocity.z > 180.0f` → выход, `onground = -1`**. То есть трасса НЕ
  выполняется, пока игрок летит вверх быстрее 180. Расшифровка `fnstsw ax; and eax, 4100h;
  jnz`: `4100h` = `C0 | C3`, переход идёт при `C0 | C3 != 0`, то есть при `velocity.z <= 180`.
- Условие с `normal[2]` собрано как `fnstsw ax; test ah, 5; jp` — переход при `C0 == C2`,
  то есть при `normal.z >= 0.7`.
- `trace.endpos` используется как `origin` напрямую: `pm[0x38] = endpos.x`, `pm[0x3C] = endpos.y`,
  `pm[0x40] = endpos.z`.
- Раскладка `pmtrace_t` подтверждена по смещениям, которые реально читает этот код:
  `allsolid +0`, `startsolid +4`, `fraction +16`, `endpos +20`, `plane.normal +32`, `ent +48`.

Следствие: зависание возможно только там, где **под точкой `origin` в 2 юнитах есть поверхность
с `normal.z >= 0.7`** — то есть верхняя кромка уступа, края стены, борта, пандус. И при этом
`velocity.z <= 180`. Чистый стрейф вдоль вертикальной стены зависания дать не может: под
`origin` пусто, нормаль стены даёт `normal.z = 0`.

### Единственные писатели `onground` (полный скан `client.dll`)

Проверены все обращения к `[reg+0E0h]` по всему модулю. Для `movetype == 3` (ходьба) writers:

| Функция | Что делает |
| --- | --- |
| `PM_CategorizePosition` `0x5FD70` | `0x5FDB6`, `0x5FE07` → `-1`; `0x5FE19` → `trace.ent` |
| `PM_Jump` `0x61930` | `0x619BF`, `0x61B18` → `-1` (прыжок срывает игр с земли) |

Все прочие вхождения — **чтения**: `PM_Move` `0x62C23`, `PM_PlayerMove` `0x5F168`,
`PM_Friction` `0x5F541`, `PM_StepSlideMove` `0x5EBF0`, `HUD_PlayerMove_0` `0x63072`,
`sub_5E1F0` `0x5E24B`, `sub_5E340` `0x5E38F`, `sub_60780` `0x60A03`.
`sub_61250` (ветка fly/noclip) пишет `onground` отдельно, но из ходьбы недостижима.

Значит выставить `onground` в ходьбе можно **исключительно** через `trace.ent` из
2-юнитовой нисходящей трассы. Никакого другого пути нет — это доказано полным сканом.

### `PM_ClipVelocity` — `0x5E7D0`

```c
backoff = DotProduct(in, normal) * overbounce;
for (int i = 0; i < 3; i++) {
    change = in[i] - backoff * normal[i];
    if (change < 0.1f) change = 0.0f;
    out[i] = change;
}
```

Любая компонента, ставшая меньше `0.1`, обнуляется. При вертикальной стене нормаль
`(±1, 0, 0)` — вертикаль не меняется. Сбросить `vz` этим путём можно только если у нормали
есть ненулевая `z` и `backoff` положителен.

### `PM_StepSlideMove` — `0x5E960`

- До **4** итераций слайда, до **6** плоскостей касания, `timeLeft` уменьшается на `trace.fraction`.
- `allsolid` → `velocity = 0`, возврат `4`.
- Плоскости в touchplane попадают только при `normal[2] > 0.7`.
- Если плоскость ровно одна, `movetype == 3` и (`onground == -1` или `pm[196] != 1.0f`):
  `overbounce = (1.0f - pm[196]) * movevars->stepsize + 1.0f`, иначе `1.0f`.
- Нулевое суммарное время движения → `velocity = 0`.
- Подтверждает: при `onground == -1` срабатывает отдельная ветка overbounce.

### `PM_CheckVelocity` — `0x5E6E0`

Клампит `velocity[0..2]` и `origin[0..2]` по `movevars->maxvelocity`; NaN обнуляется с
`PM got a NaN veloc/origi` в консоль.

### `PM_Jump` — `0x61930`

- `velocity[2] = sqrt(72000.0f)` ≈ `268.33`, умноженное на duck-штраф `(100 - duck * 0.001 * 19) * 0.01`.
- При `onground != -1` и горизонтальной скорости выше `maxspeed * 1.2` скорость режется
  до `maxspeed * 1.2` и домножается на `0.8`.
- Вход в воду: `onground = -1`, `velocity[2] = 100.0 / 62.0 / 50.0` для `watertype` `-3 / -4 / иное`,
  плюс звук шага по воде.

### `movevars_t`: оффсеты в проекте расходятся с бинарником

Реальные смещения по использованию в `client.dll`:

| Смещение | Поле | Как подтверждено |
| --- | --- | --- |
| `+0` | `gravity` | гравитация в `PM_Move` |
| `+4` | `stopspeed` | `max(speed, movevars[4])` в расчёте трения |
| `+12` | `maxspeed` | кламп длины `wishvel` в `PM_AirMove` |
| `+16` | `accelerate` | `wishspeed * accelerate * frametime` |
| `+20` | `airaccelerate` | передаётся в `PM_AirAccelerate` |
| `+28` | `friction` | `speed - movevars[28] * 1.5 * ...` |
| `+44` | `stepsize` | overbounce в `PM_StepSlideMove` |
| `+52` | `maxvelocity` | кламп в `PM_CheckVelocity` |

Проектный `cstrike1_5/structs/movevars.hpp` объявляет `maxspeed` на `8`, а `friction` на `24`,
и его же `static_assert(offsetof(movevars_t, skyName) == 68)` противоречит собственной
раскладке (при текущих полях получается `52`). **Требует правки** — любые обращения к
`movevars->maxspeed`, `stepsize`, `friction` сейчас читают мусор.

### Гипотеза (НЕ подтверждена, требует runtime-теста)

- Чтобы попасть в «промах на #1, попадание на #2» внутри одного тика, `origin` должен пересечь
  окно в 2 юнита прямо во время движения. При вертикальной скорости около 0 это достижимо:
  смещение за тик меньше 2 юнитов, и окно ловится. Значит рабочее состояние — **медленное
  снижение при большой горизонтальной скорости**, а не свободное падение.
- Гейт `velocity.z > 180` означает, что весь подъём после прыжка (`vz = 268`) вообще не проверяет
  опору. Ловить окно можно только на нисходящей ветке или после гашения вертикали.
- `PM_CheckDuck` вызывается первым в каждой категоризации и способен утянуть `origin` вниз на
  высоту приседания. Это ещё один способ искусственно опустить `origin` в окно 2 юнита —
  тот же механизм, что у duck-бага и SGS.

### Следствие для `texturebug`

Текущая реализация ищет вертикальную стену (`|normal.z| <= 0.25`) и стрейфит вдоль неё. По
подтверждённому коду это не может дать подавление вертикали: под `origin` в этом случае пусто,
а нормаль вертикальной стены даёт `normal.z = 0`.

Искать нужно **проходопроходную геометрию**, а не стену:

1. условие входа в зависание — точечная трасса вниз на 2 из `pm->origin` находит поверхность
   с `normal.z >= 0.7`, и `velocity.z <= 180`;
2. чтобы горизонталь не терялся, нужен именно тик «промах на #1, попадание на #2»: тогда
   `PM_Friction` не вызывается, `PM_PlayerMove` заменяется `PM_AirMove`, потолка `maxspeed`
   нет, а `velocity.z` всё равно зануляется;
3. практический признак такого тика — вертикальная скорость передвинулась, но не упала:
   смотрю на `origin.z` и `velocity.z` до и после.

### Wall-run отсутствует

`pm + 208` в `PM_Jump` читается как «уже бегу по стене, прыжок не обрабатывать»
(`if (pm[208] != 0) { pm->duck_flag |= 2; return; }`), а в `PM_Move` — как «не искать платформу».
Полный скан блока `0x5C000..0x63200` на записи в `[reg+0D0h]` дал **ноль попаданий**: все
совпадения — стековые кадры вида `[esp+0D0h+var_90]`. Значит поле не пишется в клиентской
prediction-копии нигде, wall-run в этой сборке не реализован.

`sub_60F00` — не wall-run, а поиск платформы для езды: обход списка касаний
(`pm + 0x20F50` счётчик, `pm + 0x20F54` массив), проверка `dword ptr [esi+64h] == -16`
на `movetype` каждого коснувшегося энтити, затем `pfnGetEntityByIndex` и трассировка.

### Окно duck_time — единственный способ отключить гравитацию

В `PM_Move` есть ранний выход, который полностью снимает гравитацию:

```c
if (pm->duck_time != 0.0f) {                 // +204
    if (pm->duck_time < 10000.0f) pm->duck_time = 0.5f;
    if (pm->duck_time != 0.0f) {
        pm->duck_time -= pm->duck_amount;     // +528
        if (pm->duck_time < 0.0f || pm->waterlevel == 0) { pm->duck_time = 0.0f; pm->duck_flag &= ~2; }
        pm->velocity[0] = pm->saved_forward;   // +104
        pm->velocity[1] = pm->saved_side;      // +108
    }
    PM_StepSlideMove(pm);
    return PM_CheckDuck(pm);                  // <- ни одного шага гравитации
}
```

`PM_Jump` выставляет `pm->duck_amount = 1280.0f` при прыжке, поэтому окно длится
`1280 / duck_amount` тиков. Внутри окна `velocity.z` не меняется вообще — гравитация не
прибавляется и не вычитается. Это **не зависание**: вертикальная скорость сохраняет то же
значение, с которым игрок вошёл в окно. Даёт только более медленное равномерное снижение
вместо ускоряющегося, то есть заметно больший запас времени на скольжение вдоль стены.

## skeethook_1_6: подтверждено на нашем hw.dll (2026-11-16)

Ниже — то, что я перепроверил на **нашем** бинаре (`hw.dll` в корне репо, Steam-билд,
imagebase `0x1D00000`, 5 секций), а не пересказ gold-sdk. Адреса даны как RVA/VA для

### glFrustum: настоящий aspect ratio (ПОДТВЕРЖДЕНО)

Слот указателя функции `glFrustum` найден по паттерну `patterns::camera_frustum` из gold-sdk
и **совпал в нашем hw.dll ровно один раз**, по файловому смещению `0x457C6` (RVA `0x457C6`,
VA `0x1D457C6`).

Проверка целостности цепочки (дизасм окрестностей):

| Что | Адрес / RVA | Статус |
| --- | --- | --- |
| вхождение паттерна (тело функции-обёртки) | RVA `0x457C6` | подтверждено, 1 совпадение |
| `call DWORD PTR ds:...` в теле паттерна | RVA `0x457C6+0x6D` | подтверждено (`FF 15`) |
| **слот `glFrustum`** | VA `0x279165C` | подтверждено |
| строка `"glFrustum"` | VA `0x1E50A14` | подтверждено |
| резолвер (`GetProcAddress`-обёртка) | RVA `0x5C954` | подтверждено |
| код инициализации | RVA `0x72FEE` | подтверждено |

Доказательство, что слот — именно `glFrustum` (дизасм `0x73000`..`0x73010`):

```
push 0x1E50A14            ; "glFrustum"
call 0x5C954              ; GetProcAddress
mov  ds:0x2791AC4, eax
mov  dword[0x279165C], eax   <-- ТОТ САМЫЙ слот из паттерна (+0x6F)
```

Рядом идут такие же блоки для `glOrtho`, `glLoadMatrixd`, `glLoadMatrixf` — строки найдены
`strings -a hw.dll`. Значит это таблица загрузки GL-функций, а слот `0x279165C` — её запись
для `glFrustum`. Слот лежит в `.data` за пределами raw-данных файла (BSS), заполняется в
рантайме — поэтому статически там нули, и патчить нужно **во время игры**.

**Сигнатура функции (ПОДТВЕРЖДЕНО по дизасму тела):**
`void __stdcall glFrustum(double left, double right, double bottom, double top, double zNear, double zFar)`
— аргументы читаются как QWORD с `[ebp+8]`, `[ebp+0x10]`, `[ebp+0x18]`, `[ebp+0x20]`,
`[ebp+0x24]`, `[ebp+0x1C]`; вызов идёт через `__stdcall` (`retn` без `add esp`).

**Настоящий aspect** = перехват по указателю, а не хук кода: подменить `*slot` на свою
функцию и масштабировать **только** `left`/`right`, оставив `bottom`/`top` нетронутыми.
`hw.dll` экспортирует только `qwgl*` (7 функций), ни `glFrustum`, ни `gluPerspective` в
экспортах нет — поэтому MinHook на теле функции не применим, только подмена слота.

Формула (из gold-sdk `aspect_ratio.cpp`, подтверждена геометрически):

```
scale = aspect * (top - bottom) / (right - left)
left *= scale; right *= scale
```

При `aspect` = желаемому соотношению (1.7778 для 16:9) горизонтальный FOV расширяется,
вертикальный остаётся прежним — объекты не растягиваются. Это НЕ то же самое, что менять
`clientdata_t::fov`: там растягиваются обе оси.

**Реализовано** в `src/features/sh_aspect.cpp` (скан паттерна → инициализация слота →
подмена при включении, возврат оригинала при выключении).

### ОПРОВЕРГНУТО: aspect через clientdata_t::fov

Предыдущая реализация брала `clientdata_t::fov`, применяла `tan(h/2) = tan(v/2) * (a / 4:3)`
и записывала результат **обратно в `fov`**. Это просто более широкий угол обзора: пиксели
растягиваются по обеим осям, вертикальный угол тоже растёт. Настоящий aspect-фикс так не
работает. Код из txfer-хука удалён, механика заменена на `glFrustum`.

9. **`sh_world_to_screen` — инвертированная проверка TriAPI**

проверочный скрипт считал смещение неверно.

Ошибка была в строке вида `off = m.start() + 0x400`. Я держал в
голове, что «raw смещён на 0x400 из-за заголовка», и прибавлял
константу. На самом деле `m.start()` в Python-регексе по всему
файлу — это уже абсолютное файловое смещение, прибавлять ничего
не нужно. Из-за лишних 1024 байт все проверки показывали
«адрес вне образа», и я решил, что паттерны указывают в середину
инструкций.

Правильный способ проверки — три шага, и все три нужны:

**1. Найти матч и убедиться, что это начало функции.**
```
55 8B EC        push ebp; mov ebp, esp      <- пролог
```
Если матч начинается не с пролога, `+смещение` будет считаться
от середины функции, и все дальнейшие выводы мусорные.

**2. Прочитать байты по смещению и убедиться, что это инструкция
загрузки адреса, а не произвольный код.**
```
A1 <addr>       mov eax, [addr]
8B 0D <addr>    mov ecx, [addr]
8B 3D <addr>    mov edi, [addr]
D9 05 <addr>    fld dword [addr]
D9 1D <addr>    fstp dword [addr]
DC 2D <addr>    fsub qword [addr]
FF 15 <addr>    call [addr]
```

**3. Проверить, что сам `<addr>` внутри образа.**
```
ImageBase = 0x1D00000, SizeOfImage = 0x1259000
```

Реальный результат проверки всех пяти паттернов:

| Паттерн | raw | смещ. | байты | адрес |
|---|---|---|---|---|
| `world_transform` | `0x7E080` | `+0xC` | `D9 05` | `0x02BC9780` ✓ |
| `screen` | `0x458F0` | `+2` | `8B 3D` | `0x02BC96E0` ✓ |
| `screen` | — | `+7` | `A1` | `0x02BC96E8` ✓ |
| `screen` | — | `+0xD` | `8B 15` | `0x02BC96E4` ✓ |
| `screen` | — | `+0x15` | `2B 35` | `0x02BC96EC` ✓ |
| `viewport` | `0x450F1` | `+2` | `8B 0D` | `0x027B775C` ✓ |
| `viewport` | — | `+0xC` | `8B 15` | `0x027B7758` ✓ |
| `chams_alpha` | `0x88200` | `+34` | `D9 1D` | `0x02732418` ✓ |
| `load_skys` | `0x4F9C2` | `+7` | `A1` | `0x0234345C` ✓ |
| `load_skys_name` | `0x4FA51` | `+2` | `68` | `0x02792644` ✓ |

Все адреса попадают в `.data` (BSS) — значит это глобальные
переменные, заполняемые движком в рантайме, а не константы и не
код. Что и ожидается: матрица вида, размеры экрана, буфер имени
неба.

Вывод на будущее: **не прибавлять константы к `m.start()`** и
всегда проверять все три шага. Иначе можно «исправить» рабочий
код в нерабочий — а это хуже, чем не трогать.
