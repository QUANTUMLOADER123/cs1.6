# Реверс CS 1.6 — антиаим, magic pitch, фактическая правда про desync и fakelag

Этот документ — исправление моей же ошибки. Раньше я написал, что антиаима
в GoldSrc «нет». Это неверно: антиаим **есть**, но он работает не так, как в
CS:GO. Ниже — что именно работает, с кодом из реальных сурсов и с
подтверждением из бинарника.

Источники: `unknowncheats.me/forum/counterstrike-1-5-1-6-and-mods/`
(несколько тредов, 2016–2017), плюс собственный дизассемблер `hw.dll`.

---

## 1. Ключевой факт: клиент строит `usercmd_t`, сервер его исполняет

```
CL_CreateMove (client.dll 0x01958CC0)  ->  usercmd_t
        |
        v
CL_SendMove (hw.dll ~0x1D19200)  ->  CLC_Move пакет
        |                              (nNewCommands + nBackupCommands)
        v
сервер: CmdStart() -> random_seed
        PM_Move()  -> из usercmd_t берётся viewangles
        FireBullets3 -> углы из pev->v_angle
```

**Что это значит:** угол, который клиент положил в `cmd->viewangles`,
уходит на сервер как есть. Сервер не проверяет, «настоящий» ли он.
Поэтому:

- антиаим **влияет на то, куда полетят твои пули** (сервер берёт угол из
  `usercmd_t`);
- антиаим **влияет на модель и на просчёт попаданий по тебе**
  (зависит от того, что сервер считает углом игрока).

---

## 2. «Magic pitch» — главная механика ⭐

Реальный код из сурсов (unknowncheats, тред «Anti Aim examples for CS 1.6»):

```c
if (bAntiAim)
{
    float flAngles = GetAntiAimAngles();

    pCmd->viewangles.x = 180;   // "180 screws up the hitbox on the server side,
                                //  so called 'magic pitch'"

    pCmd->viewangles.y = flAngles + 89;

    // движение чинится отдельно, см. п. 4
    flYaw = DEG2RAD(pCmd->viewangles.y - vecRealView.y + vecMove.y);
    pCmd->forwardmove = -cos(flYaw) * flSpeed;
    pCmd->sidemove     = sin(flYaw) * flSpeed;
}
```

**Почему `180` ломает хитбокс.** Сервер строит углы для модели и трассеров
через `AngleVectors`. Для `pitch = 180`:

```
forward.x = cos(180)*cos(yaw) -  ...  -> forward направлен ВНИЗ и НАЗАД
up.x      = ...
```

Функция `AngleVectors` в GoldSrc **не нормализует pitch** в `[-90, +90]` —
она берёт синус/косинус как есть. Значит `pitch = 180` даёт «перевёрнутую»
систему координат: `forward` и `right` меняют знак относительно нормальных.
Хитбокс головы, который сервер считает по `forward`-оси модели,
оказывается **с другой стороны тела**.

Это и есть механизм хайдшотов: **ты смотришь в одну сторону, а хитбокс
повёрнут так, что попасть в голову надо с противоположной стороны.**

### Варианты pitch из сурсов

| режим | значение | эффект |
|---|---|---|
| Down | `x = 88` | смотрим строго вниз, хитбокс головы «под» телом |
| Up | `x = -88` | смотрим вверх |
| **FakeDown** | `x = 1620` | **1620 = 4.5 * 360** → перевёрнутый хитбокс |
| **FakeUp** | `x = -1619` | то же в другую сторону |
| Spin X | `cos(t*11*pi) * 90` | качание |

Именно `1620`/`-1619` — не опечатка: это `180 + 4*360` и `-180 - 4*360`,
то есть тот же «magic pitch», но с накопленным оборотом, чтобы
**интерполяция** на клиенте противника не сгладила переворот.

### Проверка на бинарнике

`AngleVectors` доступна клиенту как `gEngfuncs.pfnAngleVectors` — таблица
`cl_enginefunc_t`, оффсет `+0x84`. Значит клиент может **предсказать**,
какой `forward`/`right`/`up` сервер получит из его углов. Это используется
для movement fix (п. 4).

## 3. Yaw-режимы (из тех же сурсов)

| режим | код | что даёт |
|---|---|---|
| Backwards | `y += 180` | модель смотрит назад |
| Static left/right | `y = 90` / `y = 270` | фиксированный бок |
| Left/right | `y += 90` / `y += 270` | сдвиг |
| Spin | `sin(t*11*pi) * 360` | вращение |
| Jitter | `rand()%100 < 10 → y += 180` | дёрганье |
| Random jitter | `rand()%100<98 → y-=180`, потом `±70` | «рандом» |
| **Fake sideways** | `y -= 91`, чёт/нечет кадр `y -= 180` | подмена на каждом пакете |

Последний — ближайший аналог CS:GO desync: **значение меняется через
кадр**, поэтому на сервер уходит «то так, то так», и усреднение
(интерполяция) даёт «размазанную» модель.

---

## 4. Movement fix — обязателен, иначе тебя видно

Если просто поставить `viewangles.y += 180`, игрок начнёт **бежать
спиной вперёд**: `forwardmove`/`sidemove` считаются в системе углов,
которые ты подменил.

Правильно (из сурсов):

```c
// 1. запомнить углы, которые были ДО подмены
Vector viewforward, viewright, viewup, aimforward, aimright, aimup;

gEngfuncs.pfnAngleVectors(old_angles, viewforward, viewright, viewup);

// 2. подменить углы для отправки
cmd->viewangles.y += 180;

// 3. посчитать новую систему
gEngfuncs.pfnAngleVectors(cmd->viewangles, aimforward, aimright, aimup);

// 4. перепроецировать move на новую систему
cmd->forwardmove = DotProduct(old_move, aimforward);
cmd->sidemove    = DotProduct(old_move, aimright);
```

Без шага 4 движение «уезжает» — именно поэтому в сурсах movement fix
встречается в **каждом** треде про антиаим.

## 5. Desync — что реально есть, а чего нет

### Есть: «псевдо-desync» через разные углы в разных пакетах

```c
// из сурсов: fake sideways
cmd->viewangles.y -= 91;
if (sendpacket)                // каждый второй пакет
    cmd->viewangles.y -= 180;
```

Модель игрока у противника получает два разных yaw → интерполяция
«размазывает» её вбок. Это **даёт** визуальный эффект desync.

### Нет: настоящего desync как в CS:GO

В CS:GO `m_angEyeAngles` и `m_flPoseParameter` разведены, поэтому
серверный хитбокс и видимая модель расходятся на **управляемую**
величину, ограниченную `GetMaxDelta()` (≈60°).

В GoldSrc:
- углы модели = `pev->angles`, которые сервер ставит из `usercmd_t`;
- хитбоксы считаются по `pev->origin` + фиксированные `mins/maxs`
  (`-16,-16,-36 .. 16,16,36` стоя), **не по анимации**;
- **отдельного «тела» и «глаз» нет.**

Вывод: **в CS 1.6 хитбокс — это коробка.** Desync может сбить
прицеливание по модели, но не создаёт «невидимый хитбокс». Отсюда
парадокс, который ты и заметил: люди «делают desync», но работает
он иначе — через `magic pitch`, а не через рассинхрон анимации.

### Что это значит на практике

| хочешь | делай |
|---|---|
| усложнить попадание в голову | `pitch = 1620` / `-1619` |
| «размазать» модель | fake sideways (менять yaw через пакет) |
| крутиться | spin yaw |
| — | настоящего CS:GO-desync нет, хитбокс — коробка |

## 6. Fake lag — есть, и вот механизм

Из дизассемблера `hw.dll`, функция отправки (`0x1D19200`):

```asm
; число новых команд в пакете
1d194f6  mov ecx,[cl.backup_commands]     ; 0x1E3AFCC
1d194fc  cmp esi,0x5                      ; состояние == 5 (in-game)
1d19512  mov edx,[cl.outgoing_command]    ; 0x2D59B30
1d19518  mov ebx,[cl.lastoutgoing_command]; 0x2D59B24
1d1951e  sub edx,ebx                      ; = сколько НЕ отправлено
1d19520  cmp edx,ecx                      ; сравнить с лимитом
1d19522  jl  ...                          ; меньше — отправить как есть
```

**Вот оно:** «сколько команд уже зажато» = `outgoing - lastoutgoing`, и
это сравнивается с **переменной**, а не с константой `15`. Значит
лимит choke задаётся переменной `0x1E3AFCC`.

Рядом:

```asm
1d1939f  fld [float 0x1E1D204]           ; = 1.0
1d193a5  fdiv [cl_cmdrate]               ; 1.0 / cmdrate
1d193ab  fadd [cl.time]                  ; + cl.time
1d193b1  jmp ...
1d193b9  mov eax,[0x2D5DA48]
1d193be  fstp [0x2D5DA44]                ; next_send_time
```

То есть время следующей отправки = `cl.time + 1.0 / cl_cmdrate`.
`cl_cmdrate` капится в **100**:

```asm
1d18ecd  cmp eax,0x64        ; 100
1d18ed0  jle ...
1d18ed2  mov eax,0x64        ; clamp до 100
```

### Что это даёт

- **минимальный интервал отправки = 10 мс** (при `cmdrate = 100`);
- `nNewCommands` вычисляется из `outgoing - lastoutgoing`, ограниченного
  переменной `0x1E3AFCC`;
- **fake lag реализуется задержкой отправки** — не отправлять пакет,
  пока не накопится N команд. Это **работает**: сервер просто получает
  пачку команд позже.

### Ограничение

Сервер исполняет все пришедшие команды подряд (в `PM_Move` нет проверки
«сколько команд пришло»). Значит fake lag даёт **не «телепорт», а
задержку**: у противника ты «замираешь», потом прыгаешь вперёд. Это
ровно тот эффект, который виден у людей в CS 1.6.

## 7. Roll

Ты прав, что roll — «у моделей». Проверяю по структурам:

- `usercmd_t.viewangles` — **три** float, и `z` уходит на сервер;
- в `PM_Move` `viewangles` используется только для получения
  `forward`/`right` — через `AngleVectors`;
- `AngleVectors` **использует** `angles[2]` (roll) при построении
  `right`/`up`.

Значит: **roll влияет на направление движения и на то, куда смотрят
твои пули**, но визуально камера не крутится (её крутит клиент по
своему `cl_view`). А вот модель противника можно крутить через
`cl_entity_t.angles[2]` — сервер присылает `entity_state_t.angles`
(vec3), и `z` в нём **есть**.

Вывод: roll реализуем как:
1. `cmd->viewangles.z` — влияет на движение (осторожно, movement fix);
2. `entity->angles.z` у **своей** модели — но сервер перезапишет своим.

## 8. Что реализовано в SDK

`src/features/sh_antiaim.cpp` — переписан:

| режим | реализация |
|---|---|
| pitch: down/up/fake_down/fake_up | `88 / -88 / 1620 / -1619` |
| pitch: spin | `cos(t*11*pi)*90` |
| yaw: backwards/left/right/spin/jitter | по таблице п. 3 |
| yaw: fake sideways | `-91`, через пакет `-180` |
| roll | `cmd->viewangles.z` |
| **movement fix** | перепроекция move (п. 4) |
| защита от стрельбы | не менять углы при `IN_ATTACK`, `IN_USE`, C4/граната |
| не в noclip/ladder | проверка `movetype` |

Ключевое: **movement fix обязателен**, без него antiaim делает тебя
бегущим задом — это худшая из возможных ошибок.

## 9. Честный итог по твоему списку

| механика | в CS 1.6 | как именно |
|---|---|---|
| **Hideshots** | **работает** | `pitch 1620/-1619` — переворот хитбокса |
| **Antiaim yaw** | **работает** | `y += 180/90/270`, spin, jitter |
| **Roll** | **частично** | влияет на движение; модель крутит сервер |
| **Desync** | **псевдо** | смена yaw через пакет; хитбокс — коробка |
| **Fake lag** | **работает** | задержка отправки, лимит в `0x1E3AFCC` |
| Double tap | нет | нужен телепорт `m_flNextAttack` на сервере |

Я был неправ в прошлом сообщении. Антиаим в CS 1.6 есть, и он
существенно отличается от CS:GO — через `pitch`, а не через
рассинхрон анимации.
